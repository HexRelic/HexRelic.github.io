Scorch for Android, version 1.0.0

Some files deserve a fire.

An offline file shredder. Scorch writes over a file's contents before it deletes it, wipes the free space other apps left behind, and strips location and camera data from photos. It has no network permission, so nothing about what you destroy can leave the phone.

Deleting a file normally removes only its entry in a folder. The contents stay on the storage until something else happens to land in the same place, and that's exactly where recovery apps look. Scorch writes over the contents first.

    What overwriting can't do.

    Phones keep files on flash memory, run by a controller chip. When an app writes over a file, the controller usually puts the new bytes in fresh cells and only marks the old ones for cleaning later. No app, this one included, can reach those old cells or make sure they're erased.

    What Scorch does do: the old contents can't be reached through the filesystem any more, so recovery apps that read the storage the usual way shouldn't find them. Seven passes are unlikely to do better than one, and each pass adds a little wear to the chip; the longer schedules are there for procedures that name them.

    So Scorch doesn't protect 100% against advanced forensic techniques: someone with lab equipment and your phone's memory chips may still find what overwriting didn't reach. It's made for recovery apps and casual snooping, not for a forensic lab.

    If something must never be recovered, keep it encrypted from the start.

    Android already encrypts your storage, and a factory reset throws the key away. That is the strongest wipe a phone has.

    Before you install.

    Is one pass enough?

    Likely, yes. On flash storage, like a phone's or an SSD, no app can be sure it rewrote the exact cells a file was kept in: the storage controller decides where each write lands, and it can keep old copies out of reach. Extra passes go through the same controller, so they don't make that any more certain. That's why a single random pass is the sensible choice; the longer schedules are there for procedures that ask for them by name.

    Does shredding wear out my storage?

    A little, like any writing. Flash memory takes a limited number of writes, and every pass writes the whole file again, so seven passes over a big file cost seven times the writes of one. Shredding now and then makes no difference you'd notice. If you shred a lot of data often, or wipe free space regularly, a single pass is the gentler choice, and the Storage wear card shows the chip's condition on phones that let apps read it.

    Why does it need All files access?

    Android's other ways in often hand an app a new copy of a file to write to, leaving the old one where it was. A shredder that wrote through them would overwrite nothing. To write over a file's own bytes, Scorch has to open it at its real location.

    Can I undo a shred?

    No, that's the point. Before anything is written you see every file, the schedule and a time estimate, you type SHRED and you unlock the phone again. To see what a job would do without risk, turn on Dry run in Settings.

    Does it work on SD cards?

    Usually. Some storage, like certain SD cards and cloud-backed folders, writes a new copy instead of overwriting in place. Scorch reads every pass back to catch that, and if the bytes don't match it stops with an error and leaves the file where it is.

    Does Scorch send anything anywhere?

    It can't: it has no network permission at all. It keeps its settings on the phone, and a crash report only if it crashed, which it shows you so you can choose to send it. Nothing about what you shredded is kept.

    How do I know the app matches its source code?

    Release builds are reproducible: building the same version from the public source gives a byte-identical app, so anyone can confirm the published app comes from that code. The build notes show how.
